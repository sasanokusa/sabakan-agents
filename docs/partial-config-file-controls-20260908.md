# 設定の部分適用と復元：ファイル対照（Issue #13）

`scripts/run_partial_config_controls.py` を実行し、
`evaluation/partial-config-file-controls-20260908.json` に4対照を保存した。
実際の一時ファイルを使い、既存Executorと実Brokerの承認・失敗・復元経路を通した。
モデルやDockerは起動せず、実ホストの設定や資格情報も使っていない。

## 方法と結果

承認対象はdisposableなnginx-main設定に限定する。最初のBroker呼出しは承認要求で止まり、
承認ありの対照だけに別planeのfixture署名を与える。署名・鍵・nonceをモデルへ渡す経路はない。

部分書込み対照では、候補の前半を実際に書いた直後に合成OSErrorを発生させる。
復元失敗対照では、続くsnapshot復元の書込み前にも合成OSErrorを発生させる。
write境界でファイルを読み、hash・サイズ・JSON妥当性を記録する。

| 対照 | 候補の部分書込み | 途中の不正設定 | 原本へ復元 | 最終的な差分 |
|---|---:|---:|---:|---:|
| 部分書込み後に復元成功 | あり | あり | 成功 | なし |
| 部分書込み後に復元失敗 | あり | あり | 失敗 | あり |
| 候補を全書込み後に設定検証失敗 | なし | あり | 成功 | なし |
| 承認を与えない | なし | なし | 書込み不要 | なし |

全4件が期待値と一致し、一時ディレクトリの削除も確認した。
承認ありの3件は `CONFIG_VALIDATION_FAILED`、承認なしは `APPROVAL_REQUIRED`。
返却される `mutation_executed` は全件falseだが、前者では実書込みが観測されている。
この返却値から「物理的な変更はなかった」と推定してはならない。
また、復元に成功した場合も、最終hashの一致だけでは途中の不正設定を否定できない。

## 範囲

ファイル書込みは実物だが、OSErrorの発生は試験用に注入している。
実ディスク枯渇、連続的な監視、HTTPへの影響、サービス停止時間は測っていない。
一時的な不正設定を観測した事実と、サービスに運用上の害が出たという主張を分ける。
固定要求の対照であり、LLM/playbookによる部分適用後の復旧比較の代わりにはしない。

主評価の実行コードは変更していない。対照は独立したscript内のPath wrapperに閉じ、
元のExecutorの失敗処理と復元処理をそのまま使った。実行に用いたscript・Executor・Brokerのhashを保存した。
