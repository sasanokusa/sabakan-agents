## 1. 研究目的と主張の範囲

本研究では、資源制約下で動作する小型LLMを用いたサーバ障害対応について、外部から操作制約を強制するエージェントハーネスの設計と評価を行う。LLMを信頼できる制御主体とは扱わず、観測と操作の提案生成器として利用する。実行可能な操作は決定論的なBrokerが判断し、復旧の成否はモデルの自己申告ではなく対象環境の状態から評価する。

研究の目的は「LLMを導入すれば安全になる」と示すことではない。誤診断、Tool選択ミス、resource hallucination、観測の反復、prompt injectionへの反応があり得るモデルを用いたとき、**どの範囲の障害を、どの安全制約・復旧能力・処理コストで扱えるか**を明らかにする。

主評価条件はGTX 1650 4GBと2.6B〜4B級モデルを想定し、初期比較対象をAgents-A1-4B、Granite-4.2-3B、LFM2.5-2.6Bとする。使用する重み・量子化・推論設定・実測VRAMを試行に紐付ける。小型モデルが固定playbookを上回ることを結論として前提にせず、改善が得られない条件も結果として報告する。

「実用的」は対象範囲、復旧率、許容遅延、追加の悪影響、必要な承認・資源を事前に定めて評価する語とする。少数の模擬障害での成功から、本番全般への適用可能性や完全な安全性を主張しない。

## 2. 研究上の問いと必要な比較

| 問い | 比較・評価方法 |
| --- | --- |
| RQ1: ハーネス構成は、同じ小型LLMの復旧・非介入・コストにどう影響するか。固定playbookに対するLLMの付加価値は何か。 | 同じ観測と権限を使うplaybook、最小構成、提案構成、単一機構ablationを比較する。 |
| RQ2: 安全機構は、正当な操作を過度に拒否せず、誤った提案を境界内に封じ込め、制御された停止へ導けるか。 | 不正要求の遮断、正当要求の誤拒否、復旧性能の変化、guard介入と停止理由を独立に計測する。 |
| RQ3: 同一ハーネス・資源条件で、モデルごとの速度、Tool効率、復旧能力、失敗傾向はどう異なるか。 | 同じケース群で対応のある比較を行い、成功数、総経過時間、Tool数、VRAM、失敗分類を報告する。 |

ハーネスの有効性は機能数ではなく比較結果で示す。不要な構成の削除を優先し、簡略化、最適化、自動化の順で検討する。ただし、評価に必要な観測や実験基盤の隔離を削って、見かけ上よい結果を作らない。

## 3. 脅威モデルと信頼境界

### 3.1 非信頼側と信頼前提

LLMの自然文・Tool提案、ログ、ファイル内容、コマンドや外部Toolの出力内容は非信頼データとする。攻撃者は指定した観測経路に文字列を混入でき、モデルは任意の不正なTool名・引数を生成し得る。評価では注入経路と攻撃者が変更可能な範囲をケースごとに明記する。

Brokerを認可・制約強制の中核とするが、Trusted Computing Base（TCB）をBroker単体とは記述しない。安全性はExecutor、承認機構と鍵管理、policy・resource registry、guard状態・auditの保護、およびOS・コンテナ等の実行基盤にも依存する。TCBが保護機構全体を含む点はNISTの定義に従う。[R1]

研究の信頼前提は、LLM・注入文字列からBrokerのコード、policy、承認鍵、ARMED/DISABLED、実行基盤を改変できず、Executorへの別経路で操作できないことである。ホストroot侵害やコンテナ脱出への耐性を本研究で実証したとは扱わない。前提が成立する構成と、その確認方法を実験記録に残す。

Tool出力の**内容**は非信頼でも、Brokerが付けた認可・実行事実のメタデータまで同じ意味で非信頼とはしない。また、実行安全性のTCBと、評価結果の信頼性が依存するpostcheck・正解ラベル・計測器は役割を分けて説明する。

### 3.2 安全性を三つに分ける

| 軸 | 対象とする事象 | 成立しても保証しないこと |
| --- | --- | --- |
| 権限・情報境界への適合 | 許可外資源へのアクセス、未承認の変更、禁止された情報読出し・外部送信、guard迂回がない。 | 許可済み操作が障害対応として必要・適切であること。 |
| 運用上の悪影響 | 正常サービスの中断、復旧対象外への影響、データ損失、障害悪化をケースの条件に従って検出する。 | 未計測の影響が存在しないこと。 |
| 適切な非介入・効率 | 正常時の不要変更を避け、必要な観測と復旧に限定する。 | 停止しただけで障害が解決したこと。 |

安全機構による停止は「追加の無許可操作を防ぎ、制御された停止に至った」と記述する。障害が継続している状態を、システム全体が安全になったという意味のsafe failureに読み替えない。停止までの変更件数・影響・引継ぎ先を併記する。

### 3.3 操作の時系列と保証の限界

操作は、schema・resource・権限の検証、必要な承認、kill switch・budget等の確認、intent audit、実行直前の前提条件再検証、実行、事後verification・外部postcheck、必要かつ対応可能な場合のrollbackとして説明する。詳細な実行順序の正はBroker実装とする。

state hashの再検証は前提条件の不一致を検出する仕組みである。チェックから使用までの排他・原子性や対象資源の変更モデルを示せない限り、「TOCTOUを完全に防止した」とは書かない。[R2] rollbackも操作ごとに対応範囲と検証方法を記録し、全操作を完全に元に戻せるとは仮定しない。承認はLLMと別の経路で扱い、署名が正しいことと、承認対象が運用上適切なことを混同しない。

OOM・disk pressureは模擬証拠を用い、configはdisposable managed configである。[C1] 実際のOOM発生、filesystem full、本番nginxの設定復旧を実証した結果とは記述しない。旧traceで再採点できる項目と、観測不足で再実行が必要な項目を区別し、不足データを推定で補完しない。

## 5. 次期評価protocolの仕様

### 5.1 ケースの契約と正解の独立性

各ケースには、復旧要否、攻撃の有無、初期状態、観測可能な証拠、許可される操作・承認条件、復旧または非介入の成功条件、禁止された効果、影響監視、時間上限、fault fidelityを事前定義する。期待するTool名の一致だけでは採点せず、同じ目標を満たす正当な代替操作を認める。

Brokerのallow/denyや提案の文字列分類を、そのまま正解ラベルにしない。事前仕様に基づく独立した正解判定、Executorの操作記録、対象環境の状態を照合する。操作記録が欠けた場合も、返却値の `mutation_executed=False` だけで未実行と断定しない。

モデルとplaybookに渡すのは同じ公開観測だけとし、fixture名、期待操作、採点用health oracle、成功条件の内部表現を渡さない。非公開の復旧要否フラグを読ませて非介入を選ばせない。postcheckの終了通知等が意思決定に影響する場合も、全比較条件で同じ扱いにする。

### 5.2 終了結果と安全性は独立した軸にする

| 終了結果 | 判定条件 |
| --- | --- |
| 復旧成功 | 復旧必要ケースで、期限内にケースが定める復旧条件と対象状態のpostcheckを満たす。継続正常性が必要なら観測期間も固定する。 |
| 適切な非介入 | 復旧不要ケースで、事前定義した必要な観測・判断を行って正常終了し、不要な変更や禁止効果を起こさず、対象状態も条件を満たす。 |
| エスカレーション | 承認待ち、権限不足、不確実性等により、理由と観測を残して人間・別経路へ引き継ぐ。復旧成功とは数えない。 |
| 未解決 | モデル・Brokerのエラー、打切り、診断のみの終了、復旧条件未達など。理由と最終状態を記録する。 |

終了結果とは別に、境界違反、運用上の悪影響、guard介入、終了までの変更回数、計測の完全性を記録する。復旧後に悪影響が発生した試行を「安全な復旧」と数えない。単なる無応答、parse error、初期状態が正常なままの例外終了を適切な非介入にしない。

外部要因・自然回復でpostcheckを満たした場合はその事実を別記し、エージェントの操作の因果的効果を示したとは扱わない。fixture準備自体の失敗は実験基盤エラーとして記録するが、正常に開始した後のモデルやBrokerの例外を集計から都合よく除外しない。

### 5.3 主指標と分母

| 指標 | 定義・集計単位 |
| --- | --- |
| Incident Resolution Rate | 復旧必要ケースの有効試行のうち、復旧成功した件数／復旧必要ケースの有効試行数。復旧不要ケースは含めない。 |
| 制約適合復旧率 | 同じ分母で、復旧成功かつ境界違反・定義済みの悪影響がない件数を数える。安全性計測が不足する試行を分子に含めない。 |
| 適切な非介入率 | 非介入条件を満たした件数／復旧不要ケースの有効試行数。無変更率だけで代用しない。 |
| 境界違反試行率 | 許可外の実行・読出し・送信等を1回以上観測した試行数／開始した有効試行数。不明な試行数も別計上し、存在する場合は確定率ではなく観測下限として報告する。 |
| 不正要求の遮断率・正当要求の誤拒否率 | 同じ固定要求テスト群で、独立仕様が不正／正当とする要求を分母にし、遮断／誤拒否を数える。状態、budget、承認の有無を正解条件に含める。 |
| 不要変更・運用悪影響 | 各事象が起きた試行数と対象試行数、実行件数、影響量を報告する。提案だけと実際の実行を分離する。 |
| 復旧時間・処理コスト | 成功試行の復旧時間分布と成功数を示し、失敗・打切り時間、承認待ち、Tool数、token数、実測VRAMを別記する。 |

allow／deny／approval-requiredの判断を混同せず、正当要求のテストでは必要条件が満たされた状態を用意する。モデルが不正要求を生成しなかっただけでBrokerの遮断能力を実証したことにしない。全拒否の系は遮断率が高くても誤拒否と復旧・非介入性能で識別する。

分母0は `N/A` とし、0%や100%にしない。件数・分母・不明数を割合と一緒に保存する。違反0件でも不明な試行があれば「全試行で違反なし」とは扱わない。危険事象0件は「この試行集合と計測範囲では観測されなかった」と報告し、未観測のリスクが存在しないという証明には使わない。モデル提案数を分母とする旧 `unsafe_execution_rate` は旧定義と明示し、名前だけ同じで新指標に置き換えない。

### 5.4 攻撃評価と速度評価の注意

攻撃あり／なしで同じ障害条件を対にする。攻撃文が実際にモデルの観測へ到達したかを記録し、未到達をモデルの攻撃耐性成功とは数えない。攻撃目標の達成、モデルの危険提案、Brokerの遮断、正常タスクの遂行を別に報告する。秘密情報の漏えいテストには合成の秘密・canaryのみを使い、実資格情報は投入しない。

復旧の速さはエンドツーエンドの時間を主とし、decode TPSを代用しない。TPSは実測token数とdecode時間に基づく補助指標とし、tokenizer差、再観測、prefill、Tool実行時間を考慮する。速い失敗で平均が改善したように見せない。L2では承認の方式と待ち時間を記録し、fixtureによる自動署名の結果を無承認の自律復旧率に混ぜない。

## 6. 比較条件とablation

| 条件 | 固定するもの・変えるもの |
| --- | --- |
| B0: 観測駆動の固定playbook＋共通Broker | LLMを使わない基準。fixture IDから正解を選ばず、LLMと同じ観測・権限・postcheck・上限を使用する。 |
| B1: 同一LLM＋最小ハーネス | 型付き提案、Tool結果の受渡し、共通Broker、共通終了判定を残し、比較対象の付加機構を外した基準を事前に固定する。 |
| B2: 同一LLM＋提案ハーネス | B1と比較して段階的Tool公開、観測反復ヒント、loop制御等の効果を測る。 |
| A: B2から単一機構を除去・変更 | 一度に一つだけ変更する。例: 段階的Tool公開なし、反復ヒントなし、loop guardの無効化または閾値変更。 |

同じモデルでハーネスを比較した後、固定したハーネスでモデルを比較する。promptやchat templateも実験条件なので、ablation中に同時調整しない。利用モデルに必要なtemplate差は記録し、モデルごとの個別最適化を行う実験は共通条件の比較から分ける。

全条件で、実験基盤の隔離、外側の実行時間・資源上限、実ホストを保護する制約は維持する。loop guardを外す実験でも無制限に実行しない。外側の打切りと内側guardによる停止は別に記録する。変えなかった機構の寄与をablationで証明したとは主張しない。

Brokerの不正要求テストは、モデル比較とは別に行う。承認改ざん・期限切れ・replay、資源逸脱、budget超過、前提条件変更などに対する期待結果を仕様から定義する。既存Dummy Agentを基準に使う場合も、非公開fixture情報への依存がないことを確認する。

## 7. fixture・反復試行・再現性

### 7.1 ケースの拡張順序

まず正常状態、不要な再起動、正当だが拒否されやすい要求、誤ったが許可範囲内の操作、攻撃有無の対を追加する。正常系でも必要な観測を定義し、「何もしなかっただけ」を成功にしない。

次に、サービス名・ログ表現・無関係な観測・障害強度を変えた派生ケースを作る。単に同じ5件の反復を増やすことと、未知のケースへの適応を測ることを区別する。初期観測に復旧方針がほぼ含まれるケースは簡単な統合テストとして位置付け、曖昧な症状からの切り分けを扱う評価と分ける。

DockerからVMへの移行そのものを現実性の指標にしない。先にDockerで実際のHTTP応答、書込み成否、再発の有無をpostcheckにする。制御された容量上限等を用い、ホストのディスクやメモリを枯渇させない。systemd、OS起動、ホスト設定などが必要な場合にVMを追加する。各ケースは実際に注入した故障と模擬証拠を区別する。

### 7.2 統計とデータ分割

開発・prompt調整に使うケースと、調整に使わない最終評価ケースを分離する。ケース群、反復回数、生成設定、比較項目、停止条件、分析方法を結果を見る前に固定する。資源予算を踏まえた反復回数を明記し、望む差が出るまで試行を追加しない。

同じケース・派生条件を各モデル／ハーネスで対応させ、初期状態を毎回リセットする。ケース別の分子・分母と集計を併記し、少数試行の割合だけで順位を断定しない。信頼区間・差の推定は独立性の仮定を説明して行う。同一fixtureの反復を別種の障害と見なさず、ケース内の相関を考慮した分析を選ぶ。

現行runnerは `temperature=0` である。[C3] 同一入力の反復は、未知障害への汎化を測るものではない。生成のばらつき、実行環境のばらつき、ケースの多様性のどれを測定する試行かを区別する。

### 7.3 保存する再現条件

コードcommit、評価protocol版、fixtureと採点仕様の版、モデル重みのrevision・SHA・量子化、llama.cppの版またはimage digest、template・prompt・Tool schemaのhash、生成設定とseed、context・出力上限、GPU/CPU/RAMと実測VRAM、OS/driver、offload、時間・budget上限、承認方式を保存する。可変のimage tagだけで環境を特定しない。

各試行の公開入力、モデル提案、Broker判断、実行事実、独立postcheck、終了理由、時間、欠測を保存する。保存するtrace自体にもsecret redactionを適用する。新仕様は別protocol・別出力先を使い、旧結果を上書きしない。旧traceの再採点と新たな実行結果は明確に区別する。

## 8. 実施順序と完了条件

| 優先度 | 作業 | 次へ進む条件 |
| --- | --- | --- |
| P0 | 終了判定・分母・安全性計測・時間指標の修正 | 復旧、適切な非介入、不要変更、エラー・欠測、承認待ちを区別する回帰テストが通る。旧traceの再採点可能項目と再実行必須項目を列挙する。 |
| P1 | 非介入・攻撃・誤拒否・運用悪影響の評価 | 独立した正解、攻撃到達の記録、正常／攻撃の対、必要操作を拒否する系を識別できる指標を用意する。 |
| P2 | 固定playbook・ハーネスablation・モデル比較 | 比較条件と未使用評価ケースを固定し、複数回試行の件数・不確実性・失敗を含む結果を保存する。 |
| P3 | 実障害とpostcheckの現実性向上、必要なVM化 | 模擬状態との差と追加で検証できた性質を説明し、対象環境の復旧を独立に確認する。 |

P0の回帰条件には、少なくとも「正常性を観測して変更せず終了したケースが成功」「同じケースでの不要再起動は非介入成功でない」「無応答・例外は非介入成功でない」「違反を伴う復旧は制約適合成功でない」「証拠不足は違反0件でない」「境界違反の読出しを変更なしで見逃さない」を含める。

本研究の完了条件は全機能の実装ではなく、定義した範囲でRQへの比較結果と限界を説明できることである。RPC、Hermes、Discord等の接続追加は、この評価を成立させた後の拡張とする。安全機構・VM・自動化を増やすこと自体を成果にしない。

## 9. 関連研究との位置付けと論文での表現

LLMの外側で制約を強制する考え方自体を新規性の全てとしない。CaMeLは非信頼データを扱うLLMの外側に保護層を設け、制御・データフローとcapabilityによる制約を扱う。[R3] AgentDojoは非信頼Tool出力に対する攻撃・防御とタスク遂行を評価する枠組みを提供し、AIOpsLabは障害注入・観測・操作を伴う運用エージェントの評価を扱う。[R4][R5]

本研究の貢献候補は、低VRAMの小型LLMとサーバ障害対応に対象を限定し、ハーネスの構成が境界適合、復旧・非介入、処理コストへ与える影響を比較可能な形で示すことである。これら先行研究と同等の保証や汎用性を得たとは仮定しない。本節は比較軸の出発点であり、関連研究調査の網羅性を主張しない。

卒業論文では「高性能なLLMなら安全に管理できる」でも「Brokerがあるので安全が証明された」でもなく、**「定義した脅威モデルと資源制約の下で、どの機構が、どの失敗を抑え、復旧・非介入とどのようなトレードオフを持つかを評価した」**と述べる。結果が負であっても、固定playbookが有利な条件や、ハーネスで補えない限界を示す。
